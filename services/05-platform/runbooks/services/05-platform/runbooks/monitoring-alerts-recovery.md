# Runbook: Збій доставки сповіщень моніторингу (Alertmanager, webhook)

**Сервіс:** `05-platform` (Monitoring)
**Шлях у репозиторії:** `services/05-platform/runbooks/monitoring-alerts-recovery.md`
**Пов'язано:** інциденти #15, #11 (звірити номери перед комітом)
**Кому адресовано:** Incident Manager, Service Owner, Change Manager

> Шляхи та імена служб типові для Debian/Ubuntu. Звірте їх зі своїм сервером перед першим використанням. Адреса webhook є секретом: не вставляйте її в тікети, коментарі та файли репозиторію.

## Коли застосовувати

Як симптом виглядає **для користувача / команди**:

- У каналі сповіщень немає жодного повідомлення понад 24 години, хоча дашборди Grafana працюють нормально (приклад: #15).
- Під час розслідування іншого інциденту з'ясувалося, що алерти не надходили (приклад: #11).

Як симптом виглядає **в моніторингу**:

- Спрацював алерт відсутності контрольного сигналу (Watchdog / heartbeat не доходить до зовнішньої перевірки).
- Alertmanager не працює, або в його журналі помилки доставки (HTTP 401, 403, 5xx).

**Пріоритет** ставиться за матрицею в `docs/slo.md`, а не за цим переліком. Орієнтир: моніторинг працює 24/7, тож якщо алерти «сліпі» під час іншого критичного інциденту, це привід підвищити пріоритет (приклад: #11). Якщо збій виявлено в спокійний час і сервіси працюють, це зазвичай P3.

## Перші пʼять хвилин: що перевірити

| # | Перевірка | Норма | Якщо не в нормі |
|---|---|---|---|
| 1 | Alertmanager запущений | `active (running)` | Запустити службу, дивитись журнал (див. команду 1) |
| 2 | Alertmanager не повідомляє про помилки доставки | Помилок 401/403/5xx немає | 401/403: оновити токен/URL (крок 1). 5xx або timeout: проблема на боці чату або мережі |
| 3 | Конфігурація валідна | `SUCCESS` | Виправити помилку, див. вивід `amtool` |
| 4 | Prometheus бачить Alertmanager і алерти справді спрацьовують | Alertmanager у списку активних, є алерти у `amtool alert query` | Якщо алерти є, а в чаті їх нема: перевірити silences (команда 5) |
| 5 | Немає активних silences, які глушать усе | Тільки ті, що створені свідомо | Видалити зайвий silence, дізнатись, хто його створив |

Команди до перевірок:

**1. Стан служби Alertmanager**

```bash
sudo systemctl status alertmanager
```

**2. Журнал на помилки доставки**

```bash
sudo journalctl -u alertmanager -n 100 --no-pager | grep -iE "error|failed|http"
```

**3. Синтаксис конфігурації**

```bash
amtool check-config /etc/alertmanager/alertmanager.yml
```

**4. Активні алерти (чи є що доставляти)**

```bash
amtool alert query --alertmanager.url=http://localhost:9093
```

**5. Активні silences і правила inhibit**

```bash
amtool silence query --alertmanager.url=http://localhost:9093
```

**6. Доступність webhook** (формат тіла залежить від чату: для Slack-подібних достатньо `{"text": "..."}`, інші системи можуть вимагати свій формат або проміжний адаптер)

```bash
curl -i -X POST -H "Content-Type: application/json" -d '{"text":"Test connectivity"}' "<WEBHOOK_URL>"
```

Не залишайте справжню адресу в історії командного рядка спільних серверів. Використовуйте змінну середовища або перед запуском очистіть запис з історії.

## Обхідний шлях

Поки канал не відновлено, моніторинг дивиться вручну:

- Раз на годину відкривати Grafana та сторінку алертів Prometheus/Alertmanager.
- Тимчасово дублювати алерти на інший канал (інший чат, email), якщо він налаштований.

Рішення про це ухвалює **Service Owner**; Incident Manager повідомляє команди, чиї сервіси зараз «без нагляду».

## Відновлення

**Крок 1. Оновити токен або URL webhook**

Якщо в журналі помилки авторизації (401/403) або змінилась адреса чату:

1. Згенеруйте новий webhook URL у налаштуваннях чату сповіщень.
2. Збережіть його у файлі з обмеженими правами (наприклад, `/etc/alertmanager/webhook_url`, власник `alertmanager`, права `600`) і не вписуйте напряму в конфіг.
3. Вкажіть у `/etc/alertmanager/alertmanager.yml` (розділ `receivers`):

```yaml
receivers:
  - name: 'chat-alerts'
    webhook_configs:
      - url_file: /etc/alertmanager/webhook_url
        send_resolved: true
```

Якщо ваша версія Alertmanager не підтримує `url_file`, вкажіть `url: '<WEBHOOK_URL>'` і не комітьте цей файл.

**Крок 2. Перезавантажити конфігурацію без зупинки**

Спочатку перевірте конфіг (команда 3), потім:

```bash
sudo systemctl reload alertmanager
```

або, якщо служба не підтримує reload:

```bash
curl -X POST http://localhost:9093/-/reload
```

**Крок 3. Надіслати тестовий алерт**

```bash
amtool alert add alertname=TestAlertReceiver severity=info instance=test-node --annotation=summary="Тестова перевірка каналу сповіщень" --alertmanager.url=http://localhost:9093
```

## Перевірка після відновлення

- У каналі сповіщень з'явилось повідомлення `TestAlertReceiver`.
- Тестовий алерт закінчиться сам після `resolve_timeout`; за потреби заглушіть його, щоб він не лишався в списку:

```bash
amtool silence add alertname=TestAlertReceiver --comment="Тест каналу сповіщень" --alertmanager.url=http://localhost:9093
```

- Watchdog/heartbeat знову доходить до зовнішньої перевірки.
- У тікеті вказано причину збою (наприклад, протермінований токен), час початку й відновлення, дотримання SLO. Інформацію передано Incident Manager для закриття.

| Якщо бачите | Кому | Які факти додати |

| Алерти «сліпі» під час іншого критичного інциденту | Incident Manager цього інциденту, якщо потрібно `КЕРІВНИЦТВУ:` | Який інцидент, чому відсутність алертів критична |

## Профілактика

**Watchdog (контрольний сигнал).** Правило, яке завжди спрацьовує, і маршрут Alertmanager, що надсилає його у зовнішню перевірку життя (Healthchecks, Dead Man's Snitch тощо). Якщо сигнал зникає, значить, зламалась сама доставка.

```yaml
groups:
  - name: watchdog
    rules:
      - alert: Watchdog
        expr: vector(1)
        labels:
          severity: none
        annotations:
          summary: "Постійний контрольний сигнал для перевірки роботи Alertmanager"
```

Потрібен також `route` у `alertmanager.yml`, який відправляє `alertname=Watchdog` у приймач heartbeat, і зовнішній сервіс, що піднімає тривогу, коли сигнал зникає. Без цього правило нічого не дає.

**Аудит токенів.** Додати перевірку терміну дії API-ключів і webhook-адрес до щоквартального чеклиста обслуговування Платформи. Створити для цього тікет з власником і строком.
