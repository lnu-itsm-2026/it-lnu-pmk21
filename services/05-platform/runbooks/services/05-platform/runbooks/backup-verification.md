# Runbook: Перевірка цілісності та усунення аномалій резервного копіювання (Backup Verification)

**Сервіс:** `05-platform`  
**Роль відповідального:** Incident Manager / Risk & Knowledge Manager / Системний адміністратор (Backup Admin)  
**Призначення:** Покрокова інструкція для інженерного складу з перевірки цілісності резервних копій, розслідування аномалій розміру (Backup Size Anomaly) та контрольного відновлення даних (P3 / P2).  
**Шлях у репозиторії:** `services/05-platform/runbooks/backup-verification.md`

---

## 1. Симптоми та тригери

Інструкція застосовується при виконанні одного з тригерів:
* **P3 (Warning):** Автоматичний алерт `BackupSizeAnomaly` про відхилення розміру нічного архіву понад **±30%** від середнього значення за останні 7 днів (аналог інциденту `#43`).
* **P2 (High):** Завершення процедури бекапу з попередженнями або помилками в журналі (status WARNING/FAILED).
* **P1 (Critical):** Повна відсутність нічного архіву або неможливість прочитати заголовок резервної копії.

---

## 2. Діагностика (Аналіз причин відхилення розміру)

Виконайте послідовно команди на сервері резервного копіювання:

1. **Перевірте статус та тривалість виконання останнього завдання:**
   ```bash
   sudo systemctl status backup_job.service
   sudo journalctl -u backup_job.service -n 100 --no-pager
Порівняйте вміст та розміри останніх двох архівів:

Bash


ls -lh /var/backups/platform/
tar -tzvf /var/backups/platform/backup_nightly_latest.tar.gz | head -n 30
Звірте перелік включених баз даних та директорій з еталонним конфігом:

Bash


diff <(tar -tzf /var/backups/platform/backup_previous.tar.gz | cut -d/ -f1,2 | sort -u) \
     <(tar -tzf /var/backups/platform/backup_nightly_latest.tar.gz | cut -d/ -f1,2 | sort -u)
3. Покроковий план перевірки та відновлення
Крок 1: Верифікація вмісту архіву
Переконайтеся, що в архіві присутні обов'язкові компоненти:

Дампи СУБД PostgreSQL (Moodle, Identity).

Системні конфігурації /etc/.

Файлові сховища користувачів.

Якщо розмір зменшився через видалення сміттєвих/тимчасових файлів з джерела (як у разі виконання runbooks/disk-cleanup.md), зафіксуйте новий розмір як новий еталон (baseline).

Крок 2: Контрольне відновлення на Staging-стенді
Для підтвердження роботоздатності архіву виконайте тестове відновлення:

Завантажте архів на тестовий сервер:

Bash


scp /var/backups/platform/backup_nightly_latest.tar.gz staging-server:/tmp/
Розпакуйте та відновіть тестову СУБД:

Bash


sudo -u postgres pg_restore -d test_moodle_db /tmp/moodle_dump.dump
Виконайте вибірку даних для перевірки цілісності:

Bash


sudo -u postgres psql -d test_moodle_db -c "SELECT COUNT(*) FROM mdl_user;"
4. Перевірка та верифікація
Підтвердження цілісності:

Кількість таблиць та записів у тестовій СУБД збігається з продуктивною базою.

Оновлення конфігуратора:

Якщо в архів потрапляли зайві директорії (наприклад, /tmp), внесіть відповідні виключення в backup_job.conf у параметр EXCLUDE_DIRS.

Оновлення статусу у тикеті GitHub:

Укажіть підтверджену причину зміни розміру, результати тестового відновлення та передайте інформацію Incident Manager для закриття тікета.

5. Профілактика та запобігання повторним аномаліям
Автоматична перевірка контрольних сум (Checksums):

Переконайтеся, що скрипт створює файл .sha256 поруч із кожним архівом:

Bash


sha256sum backup_nightly_latest.tar.gz > backup_nightly_latest.tar.gz.sha256
Регулярне розкладове розгортання (Disaster Recovery Drill):

Проводьте автоматичне або ручне тестове відновлення з резервних копій кожні 2 тижні.
